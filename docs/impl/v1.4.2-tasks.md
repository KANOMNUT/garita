### K-1. Token mechanism, including the colours that carry their own alpha

**Problem, verified.** In v1.4.1, four colours carry their own alpha: `edge` and `edge2` (`tailwind.config.js:14-15`), and `log-match` and `log-highlight` (`:35-36`). Under T42-1's `rgb(var(--c-x) / <alpha-value>)`, an unmodified use resolves to alpha 1. A scratch build on the installed Tailwind emitted `--tw-ring-opacity: 1; --tw-ring-color: rgb(var(--c-edge) / var(--tw-ring-opacity, 1))`, which is opaque white. That breaks parity for `ring-edge` (295 uses), `border-edge` (60), `bg-edge` (2), `ring-edge2` (5), `text-edge2` (3), `bg-log-match` (1) and `bg-log-highlight` (2).

**Today's modifier behaviour, verified in `dist/assets/index-*.css`.** An opacity modifier **replaces** the built-in alpha; it does not multiply it. So `border-edge/60` is `#fff9` (white at 60%), not 60% of 6%. There are 69 such sites: `border-edge/20…/70`, `divide-edge/60`, `ring-edge/40` and `ring-edge/60`.

**Decision.** There are two forms, and no function colours:

| Kind | `tailwind.config.js` value | CSS variables per theme |
|---|---|---|
| Plain colour (all others, including `surface-tint` and `scrim`) | `"rgb(var(--c-<role>) / <alpha-value>)"` | `--c-<role>: R G B` |
| Colour with its own default alpha: `edge`, `edge-strong` (was `edge2`), `log-match`, `log-highlight` | `"rgb(var(--c-<role>) / var(--a-<role>))"` | `--c-<role>: R G B` and `--a-<role>: 0.06` |

`surface-tint` and `scrim` take the plain form, per U1 §1.1. Every `bg-white`/`bg-black`/`fill-white` site carries a modifier today, so there is no bare use to preserve. `text-white` becomes `on-accent`. The CSS-only `term-selection` also carries `--a-term-selection`.

I verified the second form on the installed Tailwind in a scratch build:
- Unmodified use gives `rgb(var(--c-edge) / var(--a-edge))`.
- `border-edge/60` gives `rgb(var(--c-edge) / 0.6)`. That is byte-for-byte the v1.4.1 behaviour once the variables resolve.
- `ring-offset-panel`, `from-accent/30 to-purple/20`, `placeholder:text-dim`, `bg-x/[0.04]`, `fill-x/[0.06]` and `ring-ok/[0.18]` all resolve correctly.
- Zero `*-opacity-*` utilities are used, so ignoring `--tw-*-opacity` on the alpha form changes nothing.

**Variable format.**
- Values are decimal channel triples, space-separated (`--c-surface-panel: 18 21 29`). Hex goes nowhere in CSS.
- Dark values sit on `:root`, which also covers a missing attribute. Light values sit on `:root[data-theme="light"]` (F2), which outranks `:root`.
- Accent blocks are **theme-exclusive**, so no two blocks ever compete and file order never matters:
  - dark: `:root:not([data-theme="light"])[data-accent="<name>"]`;
  - light: `:root[data-theme="light"][data-accent="<name>"]`.
  - `blue` lives in the theme blocks.
  - That gives U1's 12 values (§8.7) in 2 theme blocks plus 10 accent blocks. Each accent block sets `--c-accent`; the dark ones also set `--c-on-accent` (F-2).
  - Do **not** write a bare `:root[data-accent=…]`: it ties on specificity with the light theme block, and in light mode it would leak the dark `--c-on-accent`.
- **Legacy names stay as aliases** (§2.1): `ok: "rgb(var(--c-status-ok) / <alpha-value>)"` and `"status-ok"` resolve to the same variable. F1 does **not** rename component classes.

**Other literal sources F1 converts.**
- `src/index.css`:
  - the body background `#06080c` becomes `surface-base` (delta D-5);
  - the body text colour becomes `ink`;
  - the scrollbar thumbs become `rgb(var(--c-surface-tint) / var(--a-scrollbar))` and, on hover, `/ var(--a-scrollbar-hover)`. Dark is 0.08/0.14 and light is 0.22/0.34 (U1 §1.4); the light `surface-tint` channel is U1's ink channel;
  - `.hairline` becomes `inset 0 1px 0 rgb(var(--c-hairline) / var(--a-hairline))`, with `--c-hairline: 255 255 255` in both themes and `--a-hairline` 0.04 (dark) / 0.70 (light) per U1 §1.4;
  - `.grain` becomes `accent` at 0.06 plus `status-purple` at 0.05, the same alphas in both themes (O-11);
  - `.row-hover` and `.row-selected` become `accent` at 0.04 and 0.08;
  - `.row-bar` becomes `accent`.
- `tailwind.config.js`: `backgroundImage.grain` and `boxShadow.hairline`/`window` are **dead**. There are zero uses of `bg-grain`, `shadow-hairline` or `shadow-window`; the classes `.grain` (1 use) and `.hairline` (17 uses) come from `index.css`. F1 deletes the dead entries.

### K-4. Native window background (T42-6) and Q42-1

- **No native change.**
  - `tauri.conf.json` has no `backgroundColor`, and a static one cannot follow a runtime preference.
  - `getCurrentWindow().setBackgroundColor()` needs `core:window:allow-set-background-color`. `setTheme` needs `allow-set-theme`. Neither is in `core:window:default` (`src-tauri/gen/schemas/desktop-schema.json:1467`). Granting either means editing `src-tauri/capabilities/default.json`, which nobody owns.
  - **`src-tauri/**` is untouched except the F5 version line.** §6 is amended to match.
- **First paint.**
  - A classic inline `<script>` in `index.html` `<head>` reads `localStorage["appearance"]` in try/catch.
  - It resolves `system` through `matchMedia`, then sets `data-theme` and `data-accent` on `<html>`.
  - `html, body { background: rgb(var(--c-surface-base)) }` comes from `index.css`, which the production build links in `<head>`, so it is render-blocking.
  - `security.csp` is `null` (`tauri.conf.json`), so the inline script is allowed. If a CSP is ever set, the script needs its hash.
  - Dev mode flashes regardless, because Vite injects CSS from JS. Judge first paint only on a bundle (§7.2).
- **No `color-scheme` property.** Setting `color-scheme: dark` would restyle native controls in dark mode, which is a parity break. Light mode is the default anyway.
- **Q42-1 answer: webview only.**
  - macOS uses `titleBarStyle: "Overlay"` and `hiddenTitle`, so the webview paints under the title bar; the traffic lights stay native.
  - Windows and Linux keep native decorations, which follow the OS. A forced theme that differs from the OS gives mismatched decorations. That is accepted and recorded in §7.2.

## 2. Contract (frontend-internal; no IPC)

### 2.1 Token roles → CSS variables

Every role in `docs/ux/00-overview.md` §6.1 **that has a consumer** (K-7.2, §1.5 O-3) becomes one CSS variable `--c-<role>` holding a decimal channel triple. It is defined twice in `src/index.css`: under `:root` (today's values, verbatim) and under `:root[data-theme="light"]` (U1's values).

`tailwind.config.js` colours become `<role>: "rgb(var(--c-<role>) / <alpha-value>)"`. Roles that carry a default alpha (`edge`, `edge-strong`, `log-match`, `log-highlight`) use `"rgb(var(--c-<role>) / var(--a-<role>))"` instead (K-1). The final role list is K-7.2. The **legacy token names stay** as aliases of their role during this release (`base`, `panel`, `card`, `edge`, `edge2`, `ink`, `mute`, `dim`, `accent`, `ok`, `warn`, `orange`, `bad`, `info`, `purple`), so the migration can be incremental and every intermediate state compiles. `edge`/`edge2` (white rgba today) map to roles whose light values are dark-on-light.

### 2.2 Accent

`--c-accent` (and, in dark, `--c-on-accent`; F-2) is set from `appearance.accent` at runtime through one attribute, `data-accent`, on `<html>`. There are 12 values (6 accents × 2 themes, U1 §4); the selectors are in K-1. No component reads the accent name. The accent blocks define nothing else (F-5 (d)).

### 2.3 Identity

`src/utils/clusterIdentity.ts`:

```ts
export const IDENTITY_ROLES = ["identity-blue", "identity-green", "identity-yellow", "identity-orange", "identity-red", "identity-purple"] as const;
export type IdentityRole = (typeof IDENTITY_ROLES)[number];
export const LEGACY_IDENTITY_ALIAS: Record<string, IdentityRole> = { accent: "identity-blue", ok: "identity-green", warn: "identity-yellow", orange: "identity-orange", bad: "identity-red", purple: "identity-purple" };
export function readIdentityColor(stored: unknown, context: string): IdentityRole; // role or alias → role; anything else → hash default of `context`
```

- `IDENTITY_ROLES` keeps the legacy index order (`accent, ok, warn, orange, bad, purple`), so the hash default is unchanged for unconfigured contexts (K-7.3b).
- `setClusterIdentity` writes `color` only when the patch sets it (K-7.3c).
- The stored record keeps every field it does not own (v1.3.1 F4's spread rule: `readOnly`, `typedConfirm`, `bulkLimit` survive).
- `CLUSTER_COLOR_CLASSES` is keyed by `IdentityRole`; class strings stay literal (Tailwind content scanning).
- `identity-demo` is reserved and not selectable (#45, backlog).

### 2.4 Hard-coded colour allow-list

After F1, the three gates in §7.1 (G1, G2, G3; sizing in K-3) hold:
- **G1**, hex/rgb in `.ts`/`.tsx` outside tests: only `src/utils/terminalTheme.ts`. In F1 that file holds the xterm object verbatim. From F2 it builds the xterm theme from resolved CSS variables (`getComputedStyle`), with a literal fallback per role for the case where a variable is unreadable.
- **G2**, Tailwind default-palette classes (`white`, `black`, `gray-NNN`, …): none.
- **G3**, hex or numeric `rgb()`/`rgba()` in `src/index.css` and `tailwind.config.js`: none. Variables are channel triples, and every colour function reads a variable.

Components carry colours as literal class strings only (K-3). Every G1/G2 site is migrated to a role. The per-site role assignment is U1 §3, with §1.5's overrides and deltas. Every assigned role's dark value equals the literal it replaces, except D-1…D-7.

### 2.5 Settings → Appearance

Section list gains **Appearance** after Diagnostics (00 §7.1 order). Controls: Theme (System / Light / Dark, radio), Accent (six swatches with names, never colour-only), a live preview row (button, link, status pills, an identity chip that **does not** change with the accent, labelled to say so).

Wireframe, spec, states, keyboard and copy follow U1 §6.1–§6.5, with the O-12 changes (no focus move from the palette; `ring-accent/70` focus style). Other points:
- **Defaults:** nothing stored, or a corrupt or unknown value, gives System + Blue. If `matchMedia` is missing or throws, System resolves to Dark.
- **Write failure** shows the U1 §6.3 `role="status"` line. The store's writer therefore returns whether `setItem` succeeded.
- The palette entry `settings-appearance` sits beside `settings-diagnostics` (`App.tsx:292`) and carries `keywords: "theme dark light accent colour"`.
