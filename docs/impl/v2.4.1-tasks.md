## 0. Minimal version, and what it skips

Minimal version (every recommended answer in section 10 taken):

- **Sidebar.** The "Custom Resources" section (one expandable row per API group, one row per CRD kind) is removed, the way v2.4.0 removed the namespace list. The existing **CRDs** row of the "Cluster" section is the entry, and it stays highlighted while a CRD's instances are shown. No new Sidebar row.
- **CRDs page.** CRDs are grouped under collapsible API-group header rows (group name and count, all expanded on open, sorted by Kind inside each group). A "Group by API group" switch, on by default and remembered on this computer, gives today's flat list back. Each row gets an **Instances** button; the CRD panel's Overview gets a **Show instances** link. Both open the existing instances list, which gains an **All CRDs** link back. Row click still opens the CRD panel.
- **Custom resource panel (new, read-only).** Clicking an instance opens a panel with Overview (kind, API version, namespace, age, phase, generation, owners, finalizers, deletion), Summary (conditions, labels, annotations, "Managed by" ArgoCD app), Events and YAML (Neat, Find, Copy). No write of any kind.
- **Rust.** Three new read commands in `crds.rs` (`get_custom_resource`, `get_custom_resource_yaml`, `get_custom_resource_yaml_neat`) with the CRD's group, version, kind, plural and scope passed flat, like `list_crd_resources`. A 404 returns `null`. An empty API group is refused, so the command cannot read core kinds (Secrets included). Conditions are parsed panic-free. No existing command gains a parameter, and no per-kind table changes.
- **Frontend plumbing.** One optional `groupBy` on `GenericResourceTable` plus a pure `groupRows`; one pure `src/utils/crds.ts`; three hooks in `useResources.ts`; a new `CustomResourcePanel.tsx` hosted by `App.tsx` beside the other two panels.

Skipped (each is a later request, or an option in section 10):

- Writes on a custom resource: delete (Q3 B), YAML save through the Review and save gate (Q3 C), Compare and Field managers (Q3 D). The contract for B and C is sketched in 2.9 so an answer can be dispatched at once.
- A header status chip derived from conditions (Q4 C); a Status column on the instances list (Q8 B); instance counts per CRD on the CRDs page (Q5 B/C).
- One palette entry per CRD kind and a launcher token for a CRD (Q6 B/C). `crd-instances` stays unmapped on the command line.
- Reading at the storage version instead of the first served version (Q7 A).
- Clickable owner references in the panel; clickable rows in the CRD panel's instance preview list; a Timeline or Map for custom resources; arrow-key navigation in the grouped table; persisting which groups are collapsed.
- A live-harness test: the harness never writes cluster-scoped objects (`live-verification.md` → Safety, T51-6) and kind ships no CRD, so it cannot create one. Section 9 and `open-items.md` carry the rows only a real cluster can close.

## 1. Decisions taken in this plan

| # | Decision | Why |
|---|---|---|
| D1 | The Sidebar keeps its **CRDs** row (Cluster section) as the only entry; it is active on both `crd` and `crd-instances`. | v2.4.0 put Namespaces as a Cluster row. CRDs already is one, so removing the tree leaves one place, as with namespaces. The highlight tells the user where they are on the instances list. |
| D2 | The custom resource panel is a new component, `CustomResourcePanel.tsx`, **not** a `SelectedResource` member. | A custom resource has a runtime group, version and kind. The five silent tables and the `Record<SelectedResource["kind"], …>` tables (`kindLabel`, `EVENT_INVOLVED_KIND`, `isHealthy`) are keyed by a static kind, and `get_resource_yaml` has no dynamic arm. A member would force placeholder rows and per-kind branches through a 3,936-line file. Precedent: the Pod panel is its own component (`DetailPanel.tsx`). |
| D3 | Selection state `selectedCr: CustomResourceSelection \| null` lives in `App.tsx`, apart from `selectedResource` and `selectedPod`. The panel renders only while `activeResource === "crd-instances"` and `selectedCr.crd.name === crdTarget?.name`. It is cleared where the other selections are cleared: the `[namespace, activeResource]` effect, the context-switch effect and Esc. | One identity per panel host, like the other two. The render guard means a stale selection can never show a panel for a different CRD. |
| D4 | The new commands take the CRD fields flat (`group, version, kind, plural, scope`), like `list_crd_resources`. The scope comes from the CRD, never from the namespace value: a cluster-scoped CRD ignores `namespace`. | Same convention as the one existing CRD-instance command; same rule as `get_resource_json` (the table's bool decides the scope, never a caller value). |
| D5 | `get_custom_resource` returns `Option`: a 404 is `Ok(None)`, like `get_pod`. Every other failure is `Err`. | The panel can say "This Widget no longer exists." instead of an error box after someone deletes the object. |
| D6 | YAML is two commands mirroring `get_resource_yaml` / `get_resource_yaml_neat`, sharing `render_obj` (`pods.rs`, made `pub(crate)`) and `NeatYaml`. Neat stays display only. | One command per output shape (agent rule); the same neat rules as every other kind. |
| D7 | Grouping is a generic optional `groupBy` on `GenericResourceTable`, with a pure `groupRows` in `tableRows.ts`. | Search, sort, selection, the X-1 row button, the read-only strip, the 403 card, the count badge and the delete column are reused, not rebuilt in a CRD-only table. |
| D8 | The Events tab reuses `get_resource_events` with `kind = crd.kind`. No Rust change. | It already filters `involvedObject.name` and `involvedObject.kind`, and lists all namespaces when the namespace is `""` (a cluster-scoped object). |
| D9 | Conditions are parsed in Rust by a pure, panic-free function. First entry per `type` wins; the message goes through `operation_message_display` (2000 characters, cut by characters, never bytes). | A custom resource's `status` is untrusted input and release builds abort on panic (hard rule). `ConditionsTable` keys rows by `type_`, so duplicates must not reach it. |
| D10 | An empty API group is refused by the new commands. | A CRD always has a group. Without the check, a webview-supplied `group: ""`, `plural: "secrets"` would read a core Secret with no reveal and no `secretReadOptions`, which breaks the Secret hard rule at the IPC level. |
| D11 | The instances list (`list_crd_resources`, `CRDResource`) is unchanged. | The panel needs only the row's identity. A Status column is Q8. |
| D12 | Docs land in task D1 after the code, on this branch, before the release commit. | v2.3.0 (R4) and v2.3.1 (D1) precedent: wave-1 agents never share a doc file, and D1 greps every claim against merged code. No release commit exists without the docs. |
| D13 | No `log_read` call in the new commands. | `diagnostics.md`: Debug read logging covers exactly three commands, "not every read". |
| D14 | Removing the Sidebar tree also removes its always-mounted `useCRDs` observer. | Today the Sidebar polls `list_crds` every 60 s on every page. After this, `["crds", ctx]` is observed only by the CRDs page and Who can (while visible). Noted so nobody re-adds an app-wide observer. |

Pure functions (each in `mod tests`; no `unwrap`, `expect` or indexing outside `#[cfg(test)]`):

```rust
/// Validates a request before any network call. Returns the ApiResource and the namespace to use
/// (`Some(ns)` for a namespaced CRD, `None` for a cluster-scoped one, whose namespace is ignored).
/// `label` in messages is `kind`, or "custom resource" when `kind` is empty.
/// Errors, exactly:
///   group ""                          -> "Failed to get {label}: a custom resource needs an API group"
///   version / kind / plural / name "" -> "Failed to get {label}: missing {version|kind|plural|name}"
///   scope "Namespaced", namespace ""  -> require_namespace's message: "{kind} is namespace-scoped and requires a namespace"
///   scope not "Namespaced"/"Cluster"  -> "Failed to get {label}: unknown scope '{scope}'"
fn cr_request<'a>(
    group: &str, version: &str, kind: &str, plural: &str,
    scope: &str, namespace: &'a str, name: &str,
) -> Result<(ApiResource, Option<&'a str>), String>;
// Builds the ApiResource with resource_edit::api_resource_for and checks scope with resource_edit::require_namespace
// (both pub(crate) already).

/// `status.conditions` entries that are objects with a non-empty string `type`, in order, first per type wins.
/// `status`: a string verbatim; a bool as "True" / "False"; anything else "Unknown".
/// `reason`, `lastTransitionTime`: strings verbatim, else "". `message`: a string through
/// argocd::operation_message_display (pub(crate) already), else "".
/// Returns [] when `status` is None, not an object, or has no `conditions` array.
fn cr_conditions(status: Option<&serde_json::Value>) -> Vec<ResourceCondition>;

/// The panel shape. `ar` supplies apiVersion and kind when the object's TypeMeta is absent.
fn cr_detail(obj: &DynamicObject, ar: &ApiResource) -> CustomResourceDetail;
```

### 2.3 Commands: Rust param ↔ JS arg

Every name is one lowercase word, so Tauri's camelCase mapping is the identity. All parameters are required: these are new commands with one caller each, not additive parameters on an existing command (CLAUDE.md, `Option<T>` rule).

| Command | Rust params | JS args (`invoke`, in `useResources.ts` only) | Returns |
|---|---|---|---|
| `get_custom_resource` | `context: String, group: String, version: String, kind: String, plural: String, scope: String, namespace: String, name: String` | `{ context, group, version, kind, plural, scope, namespace, name }` | `CustomResourceDetail \| null` |
| `get_custom_resource_yaml` | the same eight | the same eight | `string` |
| `get_custom_resource_yaml_neat` | the same eight | the same eight | `NeatYaml` |
| `get_resource_events` (unchanged) | `context, namespace, name, kind: Option<String>` | `{ context, namespace, name, kind: crd.kind }` | `K8sEvent[]` |
| `list_crds` (Q7 A only) | unchanged | unchanged | `CRD[]` with `read_version` |
| `list_crd_resources` (unchanged) | unchanged | unchanged; `version` from `crdReadVersion(crd)` | `CRDResource[]` |

Values the frontend sends: `group`, `kind`, `plural`, `scope` from the `CRD` row; `version = crdReadVersion(crd)`; `namespace = item.namespace` (`""` for a cluster-scoped object); `name = item.name`.

## 9. Risks

| Risk | Mitigation |
|---|---|
| The container cannot build the Tauri crates (no `webkit2gtk-4.1`, no `node_modules`), so R1 cannot run `cargo check` | Q9. `npm ci` fixes `node_modules`. R1 is not dispatched until the Rust gates can run somewhere. |
| A conversion webhook fails for the version Garita reads at | The panel shows the API error verbatim with Retry; Q7 A reads at the storage version, which never needs conversion. |
| A huge custom resource (a large `status`) makes the YAML tab slow | Same as any kind today; YAML is fetched only on its tab; `YamlFind` caps matches. |
| A CR with dozens of conditions or long messages | Messages cut at 2000 characters (D9); the table wraps. |
| A group header breaks the table's keyboard model | The header is a separate native button; the X-1 row button stays in the name column; W1R checks focus order. |
| Users miss the Sidebar tree | The CRDs row stays and highlights on instances; Q6 B adds a keyboard path through the palette if wanted. |
| No live test of the new reads | Unit tests on every pure step; 6.3 items 3 to 6 on a real cluster; `open-items.md` rows. |

## 10. Questions for the user

Each question lists options and a recommendation. Section 0 assumes every recommendation; a different answer becomes an amendment at the top of this file before dispatch.

**Q1. How do you reach a CRD's objects once the sidebar tree is gone?**
- A. Row click keeps opening the CRD's own panel; each row gets an **Instances** button, and the CRD panel gets a **Show instances** link. Both open the objects list. *(Recommended: one click from the page, the CRD panel keeps working, the same pattern as "Show pods in this namespace".)*
- B. Row click opens the objects list directly (drill-down, like the old tree); the CRD's own panel moves behind a small details button on the row.
- C. Only the **Show instances** link in the CRD panel (two clicks, nothing new on the row).
- D. A, plus a slim sidebar entry (for example a "Custom resources" row) that opens the grouped CRDs page.

**Q2. How should the CRDs page show the grouping?**
- A. Collapsible header rows per API group with a count, all expanded on open, Kind A-Z inside each group, and a **Group by API group** switch (on by default, remembered on this computer) that brings back today's flat list. *(Recommended.)*
- B. As A, but always grouped (no switch).
- C. Today's flat table plus a "Group" filter menu (pick one or more API groups).
- D. Two panes inside the page: API groups on the left, the selected group's CRDs on the right.

**Q3. What can the custom resource panel do?**
- A. Read only: Overview, Summary (conditions, labels, annotations, Managed by), Events, YAML (Neat, Find, Copy). *(Recommended for v2.4.1: it is what "view detail" asks for, and it adds no write path.)*
- B. A, plus **Delete** (row trash and panel trash, standard confirm, Background propagation, journal entry). About one Rust command and one hook more (2.9).
- C. B, plus **YAML edit and save** through the Review and save preview. Needs the shared YAML save path in `pods.rs` to accept a custom resource; larger and riskier (2.9).
- D. C, plus Compare and Field managers.

**Q4. How should `.status` render?**
- A. Conditions in Summary with the shared Conditions card coloured as for Deployments (True green, False red, for every type); `status.phase` (or `status.state`) as a line in Overview; no header chip.
- B. As A, but only the `Ready` condition is coloured and every other type's status is plain text, because Garita cannot know whether "False" is good for a custom type (Flux's `Stalled: False` is healthy). *(Recommended.)*
- C. B, plus a header chip from the `Ready` condition (Ready / Not ready).
- D. No status parsing; the YAML tab only.

**Q5. Should the CRDs page show how many objects each CRD has?**
- A. No. Each count is one list request per CRD (150 CRDs = 150 requests per refresh); the CRD panel already shows "N total". *(Recommended.)*
- B. Counts only for CRDs in expanded groups, fetched once, no polling.
- C. A count for every CRD, polled.

**Q6. Command palette (Cmd/Ctrl+K) and the `garita` command line?**
- A. No change: the palette keeps its "CRDs" row, `garita crd` opens the CRDs page, and saved searches per CRD keep working unchanged. *(Recommended.)*
- B. The palette gains one entry per CRD kind (for example "Widget (acme.io)") that opens its objects: the keyboard replacement for the sidebar tree.
- C. B, plus `garita <plural>.<group>` (a CRD name) opens its objects.

**Q7. Which API version should Garita read custom resources at?**
- A. The CRD's storage version when it is served, else the first served version (one new field on the CRD row). Reads never go through a conversion webhook. *(Recommended.)*
- B. Keep today's rule: the first served version in the order the CRD lists them (can be an old `v1alpha1`).

**Q8. Should the objects list gain a Status column?**
- A. No; status is in the panel. *(Recommended for the minimal release.)*
- B. Yes: a column from the `Ready` condition, else `status.phase`. Needs two output fields on each list row and the parsing from Q4 per row.

**Q9. Where do the Rust checks run?** This container has no `webkit2gtk-4.1` development packages, so `cargo check` and `cargo test --lib` cannot build the app crate here.
- A. Add the CI package list to this environment's setup script: `libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev libssl-dev patchelf` (from `.github/workflows/ci.yml`). *(Recommended: the agents can then run every gate themselves.)*
- B. You run `cargo check` and `cargo test --lib` on your machine after R1 and after REL, and report the result.
- C. Skip the Rust gates. *(Not recommended: R1 is new Rust code that parses untrusted input.)*

**Q10. The release commit and the GitHub Actions quota.** Team protocol says the main session asks you about the commit that will be tagged.
- A. The release commit carries no `[skip ci]`, so pushing the tag runs `release.yml` at once (needs Actions minutes). *(Recommended if the quota is back.)*
- B. Keep `[skip ci]`; after pushing, dispatch the release by hand from the tag when minutes allow: `gh workflow run release.yml --ref v2.4.1 -f tag=v2.4.1`. *(Recommended if the quota is still out.)*
- C. Build installers by hand and upload them. *(Not recommended: a hand-made release has no signed updater files, so every installed copy's update check fails while it is the latest release.)*
