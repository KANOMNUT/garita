## New findings

### N1 (P1, FRONTEND): the launch strip may never be announced

Problem: `LaunchNoticeStrip` is mounted with its text already inside `role="status"`. Many screen readers announce changes to an existing live region, not a region that appears with its content, so a forwarded request that arrives while the user is looking at the terminal could be silent (WCAG 4.1.3 Status Messages). The deferred state, where the user has to act (Go now), is the worst place to miss.

Fix: App already has a persistent polite region (`announcement` / `setAnnouncement`, `role="status" aria-live="polite" className="sr-only"`). In `applyLaunch`, wherever `setLaunchNotice` is set with lines, also call `setAnnouncement(lines.join(" "))`. Keep `role="status"` on the strip off (change it to `role="region" aria-label="Command-line request"`, as `UpgradeSeedBanner` does) so it is not read twice.

### N2 (P2, FRONTEND): deferred strip hides context/namespace/ignored problems

Problem: while deferred, the strip shows only the deferral line (`deferredLine`). Unknown-context and ignored-token lines appear only after Go now, so the user presses Go now without knowing part of the request was dropped.

Fix: in the deferred branches (`App.tsx`, both `setLaunchNotice({ lines: [deferredLine(plan)], held: a })` calls) use `lines: [deferredLine(plan), ...(plan.ignoredLine ? [plan.ignoredLine] : [])]`. Context-not-found lines already appear because that case has `plan.context === null`; if the plan is otherwise empty it falls through and shows them. Leave the namespace check for Go now (it needs I/O).

### N3 (P2, FRONTEND): status prose breaks mid-word

Problem: `CommandLine()` uses `break-all` on the status and helper `<p>` elements, so ordinary sentences wrap in the middle of words at narrow widths.

Fix: use `break-words` on those two `<p>` classes (`SettingsView.tsx` around the `v.text` and `v.helper` lines). Keep `break-all` only on the `<code>` blocks.

### N4 (P2, SITE): the hero SmartScreen sentence reads as applying to every platform

Problem: `macOS (Apple Silicon), Linux (x86_64) and Windows (x86_64). Unsigned: Windows SmartScreen will warn.` is ambiguous for macOS and Linux visitors, and the macOS install section already says its own app is ad-hoc signed.

Fix: `macOS (Apple Silicon), Linux (x86_64) and Windows (x86_64). The Windows installers are unsigned, so SmartScreen will warn. Free and open source under Apache-2.0.` The Windows-branch note and `#d-win` keep the preflight sentence verbatim.

### N5 (P1, FRONTEND): CHANGELOG leaves out the Windows installers and Scoop

Problem: [Unreleased] describes the command and Settings but not what the release is named for: the unsigned Windows `.msi` and setup `.exe` (with the `garita` command on PATH), the site downloads, the Scoop manifest, and the Homebrew cask `binary` stanza. Keep a Changelog is "shipped items only", so this must wait for a real Windows bundle check (open-items rows) or state the limit.

Fix, once the Windows bundle rows are observed (otherwise omit and say so in the release notes): under Added,

> - **Windows installers.** `Garita-windows-amd64.msi` and `Garita-windows-amd64-setup.exe` are published with each release and add the `garita` command to your PATH. They are unsigned, so Windows SmartScreen will warn. A Scoop manifest is published on the project site. Installing updates from inside the app is still macOS-only.
> - **Homebrew** installs the `garita` command with the cask.

### N6 (P2, FRONTEND): N9 is ARIA-weak

Problem: `aria-labelledby` on a `<code>` element does not give it an accessible name (the `code` role prohibits naming), so assistive tech may ignore it. It is harmless and mandated by N9.

Fix (optional, keep N9 as is): wrap `CopyLine`'s content in `<div role="group" aria-labelledby="cli-status">` so the label has an element that can carry it.

### N7 (P1, FRONTEND): README says nothing about Windows or the command

Problem: preflight #11 and F3 call for the Windows downloads (with the SmartScreen sentence) and the launcher per OS in README. `git diff f9254b4..HEAD` shows no README change, and README has no Windows or `garita` command text.

Fix: add, under the install section, the same three lines as the site (`Garita-windows-amd64-setup.exe` or `.msi`; `Unsigned: Windows SmartScreen will warn. Choose "More info", then "Run anyway".`; `After installing, open a new terminal window to use the garita command.`) and the Scoop line. One sentence for the command: `garita [--context <name>] [-n <namespace>] [kind]` opens the app; on macOS install it from Settings → Command line. No promise of public downloads beyond the links already used for other platforms.
