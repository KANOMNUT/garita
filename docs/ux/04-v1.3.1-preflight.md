## F1. ConfirmModal growth

### UXP-1 (F1, F3) blocks F1

Evidence. F3 requires initial focus on "Back to editor" (brief F3, #10), and F1 adds an initial-focus override `"cancel" | "primary" | "input"`. But the Cancel label is hard-coded: `ConfirmModal.tsx:225` (`closeLabel` is "Cancel", or "Close" in `result`/`error`). There is no `cancelLabel` prop. The only way to rename it today is a custom `footer`, and a custom footer drops `cancelRef` (`ConfirmModal.tsx` default footer only), so the `"cancel"` focus override has nothing to focus. The initial-focus effect picks `requireTyping ? input : destructive ? cancel : primary` (`ConfirmModal.tsx:141-145`).

**Proposed:** add `cancelLabel?: string` to F1; the focus override wins over the derived rule.

Detail. F1 adds an optional `cancelLabel?: string` (default stays Cancel/Close). The `initialFocus` override wins over the derived rule. `"cancel"` targets the default Cancel button. A host with a custom `footer` marks its own back button `data-modal-cancel` and the override focuses `[data-modal-cancel]` when present. PREVIEW-GATE passes `cancelLabel="Back to editor"`.

### UXP-2 (F1) note

Evidence. In `ConfirmModal.tsx` only `children` scrolls (`:251` caps the card at `max-h-[90vh]`); status, typed input and footer are pinned. F1 puts slot 6 (kubectl equivalent, multi-line, one line per namespace in the drain case) and slot 7 (notice) into that pinned zone. An expanded disclosure plus an acknowledgement checkbox can squeeze the scrolling body to nothing at `lg`. Also, `blocked` (`:119`) and the reset effect (`:124`) know only about typing, pending and host-disabled.

**Proposed:** slot 6 collapsed by default and height-capped; the acknowledgement joins `blocked` and resets with `typedValue`.

Detail. Slot 6 renders collapsed by default; its expanded content gets `max-h-40 overflow-auto`. The acknowledgement checkbox is pinned above the typed input. Add `!acked` to `blocked` (so `⌘↵` inherits it), reset `acked` to false in the same effect that resets `typedValue`, and use the existing `aria-disabled` path with `confirmDisabledReason` rather than `disabled`.

## F2. Log View group (most effort here)

What shipped in v1.3.0 that F2 builds on: `LogSourceBar` (Source group, shared), Range/Timestamps/zone with per-viewer remembered prefs (`utils/logSource.ts`), glyph-letter level chips with no counts (`LogViewer.tsx:344-364`), one "filter…" field plus a regex toggle that both filters and marks (`:246-254`, `:367-388`), a follow toggle, a Download button, `f`/`End` in the log region (`:270-281`), the Esc-in-field rule (`:263-268`), per-stream ended/error/start_error states with Reconnect/Retry (`:450-487`), and in `MultiLogViewer` per-pod stream state (`utils/podStreams.ts`), the pod tag (`utils/logSource.ts` `podTags`) and the 20-pod cap ordered by D-L7.

### UXP-3 (F2) blocks F2: MultiLogViewer has no View group at all

Evidence. `MultiLogViewer.tsx:261-275` renders only "N pods", a follow button, the arrival-order note and a line count. There are no level chips, no filter field, no wrap, no Download. Brief F2 lists the View group once, then under "MultiLogViewer" lists only the Pods popover and the cap table. 02 §3.7 says Multi has the same two groups. Reading the brief alone, an engineer builds the View group for `LogViewer` only.

**Proposed:** build the View group once as a shared `LogViewBar` + hook and mount it in both viewers; Multi gets Download and wrap (default on).

Detail. Build the View group once, as a shared component in the `LogSourceBar` mould (`LogViewBar`, same `role="group"` and same 9.5px uppercase sub-label style, labelled "View: filters the lines already loaded"), with the state in a shared hook, and mount it in both viewers. Multi specifics:

- Wrap defaults to **on** in Multi, because the shipped body already wraps (`MultiLogViewer.tsx:394`, `whitespace-pre-wrap break-all`). The single viewer keeps its default off (`LogViewer.tsx:124`).
- Download in Multi writes `{podName} {raw}` per line (the full pod name, then the raw line). Filename `{namespace}-{container}-{n}pods.log`, with `-filtered` appended for "Visible lines". There is no workload-name prop and none should be added.
- The visible "N lines" count moves into the shared status line (UXP-9).

### UXP-4 (F2) blocks F2: matching and marking run on the wrong text, and the renderer corrupts HTML

Evidence, matching. The shipped filter tests `l.raw` (`LogViewer.tsx:250-253`). With Timestamps on, `raw` begins with the ISO timestamp, while the screen shows a formatted local time (`:523`). Searching `2026` keeps every line and marks nothing. 02 §6.3 and §5.1 say "raw line" to mean "not the JSON summary", not "including the Kubernetes prefix".

Evidence, rendering. `highlightText` (`:63-76`) HTML-escapes the line first and then runs the user's regex on the escaped string, then injects via `dangerouslySetInnerHTML` (`:531`, `:539`). Searching `quot`, `amp`, `lt`, `gt` or `039` matches inside entities and breaks the markup; `"`, `<` and `&` can never match. F2 triples the number of marked fields (Include tint, Highlight tint plus underline, active match outline), so extending this function multiplies the problem. The regex is also rebuilt per line per render (`:250`).

**Proposed:** match Include, Exclude and Highlight on `ParsedLogLine.body`, compile each regex once, and render marks as React segments instead of `dangerouslySetInnerHTML`.

Detail.

- Include, Exclude and Highlight match against `ParsedLogLine.body` (the line without the Kubernetes timestamp prefix; `logParse.ts:11`), never `raw` and never escaped text. Filters note copy: "Filters match the line text, including any JSON. The Kubernetes timestamp isn't searched."
- Compile each field's `RegExp` once per (text, regex, case) with `useMemo`. Invalid pattern: fall back to plain text (shipped behaviour, `:251`) with the spec copy under that field. Ignore zero-length matches (`.*`, `x*`) so they neither mark nor count.
- Replace `dangerouslySetInnerHTML` with segment rendering: compute `[start,end,kind]` ranges on `body`, render React spans. For the legacy `HH:MM:SS.fff LEVEL msg` shape, which renders as three columns (`:525-535`), map ranges across `appTs` / `word` / `msg` by offset so a match in the level word is still marked.
- Highlight "Match n of m" counts only lines that survive Include, Exclude and level filters (hidden lines cannot be navigated to).

### UXP-5 (F2) blocks F2: rows are keyed by array index, but the buffer is a ring

Evidence. Rows use `key={i}` (`LogViewer.tsx:521`, `MultiLogViewer.tsx:383`). The buffer drops the oldest lines once 5,000 are held (`useBoundedLines.ts`, `utils/logBuffer.ts`), so indexes shift under every row while streaming. Per-line JSON expansion ("at most 200 expanded; the 201st collapses the oldest"), the expanded-row set and the current highlight match all need a stable line identity. `ParsedLogLine` has none; it carries only `json: boolean` (`logParse.ts:20`), not the parsed object.

**Proposed:** stamp a viewer-local `seq` on each pushed line and key rows, the expanded-JSON set and the active match by it.

Detail.

- Stamp a viewer-local monotonic `seq` at push time (wrap the parsed line; reset the counter on `clear()`), key rows by `seq`, hold the expanded rows in a `Set<seq>` (insertion order gives "collapse the oldest"), prune entries below `lines[0].seq` after a flush, and anchor the active match by `seq`.
- Parse JSON lazily for visible, expanded or summarised rows only, and cache per `seq`. Do not parse 5,000 lines per render.
- JSON summary rule (the spec leaves it open). Message = the first present of `msg`, `message`, `log`, `event`. Level = the line's existing `word`. Then up to 6 remaining top-level scalar keys as `key=value`, skipping the level keys and `ts`, `time`, `timestamp`, `@timestamp`. Values over 120 characters truncate with "Show full value" (02 §3.5). The Kubernetes time column stays.

### UXP-6 (F2) blocks F2: layer-registered popovers can strand Esc, `r` and ⌘K for the whole app

Evidence. The brief makes the compact Filters popover a modal layer. `App.tsx:188` returns early from the global key handler whenever `isModalOpen()` is true, which also disables the Esc branch at `:197-214`. A popover is not a modal: no scrim, no focus trap, and `ConfirmModal`'s trap does not apply (`ConfirmModal.tsx:182-208` is guarded by the dialog's own `isTopmost()`). If the user clicks into the log region while the popover is open, the layer stays registered, nothing closes it, and Esc does nothing anywhere until the trigger is clicked again.

**Proposed:** one shared popover primitive for Filters, Pods and Download that registers a layer and closes itself on Esc, outside pointerdown and focus-out.

Detail. One shared popover primitive for Filters, Pods and Download (a menu is a popover too). It calls `useModalLayer(open)` and closes on: Esc (window keydown, capture, only when `isTopmost()`, `stopPropagation`, focus back to the trigger); outside `pointerdown`; focus leaving the popover (`focusout` whose `relatedTarget` is outside); and the viewer crossing the compact threshold. Esc inside a popover field behaves as the toolbar does today (`LogViewer.tsx:263-268`): clear the text if any, otherwise close the popover. The compact threshold is the viewer's own width (a `ResizeObserver` on its root; the panel is resizable 320 to 900 px via `useResizablePanel`), not `window.innerWidth` and not a media query.

### UXP-7 (F2) blocks F2: "Following" must stay honest when pods are hidden

Evidence. CLAUDE.md: "Following" is honest only while `anyStreaming`. The in-region dot is gated correctly today (`MultiLogViewer.tsx:398`, `utils/podStreams.ts:45`). The Pods popover adds instant per-pod hide, which is a view filter: hidden pods keep streaming. If `anyStreaming` is computed over all active pods, a hidden pod that is still streaming keeps "Following" alive after every visible pod's stream has ended, and the idle line ("All streams ended", `podStreams.ts:54`) never appears.

**Proposed:** compute Following, idle text and the status word over the shown pods only; strips keep counting every streaming pod.

Detail. Hide/show never enters the effect key (`podsKey` stays the joined streaming set). The failed/ended strips and "Tailing n of m" keep counting **all** streaming pods (they report stream health, a Source fact). The Following dot, `idleText` and the status-line word use `summarizePodStreams` over the **shown** pods only. In the Pods popover, rows for pods whose stream is not streaming carry a text suffix, "ended" or "couldn't be tailed" (no colour-only state). The existing Reconnect and Retry buttons stay where they are.

### UXP-8 (F2) blocks F2: narrowing to zero pods removes the toolbar that would undo it

Evidence. `MultiLogViewer.tsx:211-218` early-returns a bare empty state ("No pods to tail." / "This workload has no running pods.") that drops the whole toolbar. With node/zone narrowing a user can pick a value that later matches nothing (the pod list re-polls every 15 s and pods move), and the controls to clear it are gone. The second line of copy is also false in that case. The cap logic runs on the un-narrowed list: `ordered.slice(0, MAX_STREAM_PODS)` (`:63-64`) and the notice tests `pods.length > MAX_STREAM_PODS` (`:282`).

**Proposed:** narrow before ordering and capping, always render the toolbar, and show "No pods match {node x · zone y}." with "Clear narrowing" at zero.

Detail.

- Narrow first, then `orderPodsForStreaming`, then `slice(0, MAX_STREAM_PODS)`. The notice tests the matching count.
- Always render the toolbar. When narrowing leaves 0 pods, the log region shows "No pods match node {x} · zone {y}." with a "Clear narrowing" button. Keep the shipped empty state only when the workload itself has 0 pods.
- Replace the shipped cap copy (`:284`) with the spec's two cases, and keep the shipped, still-true D-L7 clause: no narrowing, "Streaming 20 of 45 pods. Narrow by node or zone to choose which. Pods that aren't ready or have restarted are tailed first." Narrowed over the cap, "Streaming 20 of 31 matching pods. Narrow further to see the rest."

### UXP-9 (F2) blocks F2: the 02 status line copy is false at the default range

Evidence. 02 §3.1 and §5.1: "37 of 5,000 lines · searching the last 5,000 lines". At the default "Last 200 lines" at most 200 lines are loaded, so both the denominator and the note are untrue. The shipped count is `{visible.length} lines` (`LogViewer.tsx:391`; Multi `:274`). The honesty about the cap already exists as the strip at `:444-448` (and `MultiLogViewer.tsx:361-365`), and the Download tooltip at `:397`. 02 also shows "● Following" in the status line, but the shipped follow toggle (`:340`) and in-region indicator (`:545-550`) already carry it.

**Proposed:** count is "{loaded} lines" or "{visible} of {loaded} lines"; no always-on "Searching the last 5,000 lines." note; reuse `liveStatus` as the visible status word.

Detail. The cap strip semantics are already decided by v1.3.0 brief section 1.5 item 1 (it counts only lines dropped while following).

- Make the existing `liveStatus` text (`:318-322`; Multi `streamStatusText`) visible as the status word, in addition to the sr-only region. It already says Following only while streaming, "Paused", "Stream ended" and "Log stream failed". Do not add a second Following element.

### UXP-10 (F2) note: the filtered-empty state lacks the count and the action

Evidence. Single: `LogViewer.tsx:503-505` says "No lines match. Loaded lines are hidden by the filters." with no count and no button. Multi shows `emptyLogsText` only when `lines.length === 0` (`MultiLogViewer.tsx:377`); `emptyLogsText` is wrong for the filtered case.

**Proposed:** "No lines match. {n} loaded lines are hidden by the filters." plus "Clear filters".

Detail. When `lines.length > 0 && visible.length === 0`: "No lines match. {n} loaded lines are hidden by the filters." plus a "Clear filters" button (same action as the strip's "Clear all"). Check this case before `emptyText` in Multi. If every pod is hidden in the Pods popover: "All pods are hidden." with "Show all".

### UXP-11 (F2) note: three small definitions the spec leaves open

1. **"Filters (n)"** (compact mode): n is the number of chips in the active-filter strip other than Include. Wrap and JSON are display modes and do not count.
2. **Regex and case in compact mode** live inside the popover, so Include would silently change meaning while looking plain. When either is on and the popover is closed, the strip shows `regex` / `case` chips, each removable.
3. **Level chip counts** count loaded lines that pass Include and Exclude (not the level filter itself), so a chip's number says what toggling it would change. Compute once per flush with `useMemo`, not per render.

### UXP-12 (F2) note: chip colours and pod-tag colours disagree with the spec's own roles

Evidence. The INFO chip is `ok` green (`LogViewer.tsx:348`) while the INFO word is `text-info` (`:16-23`) and INFO lines are plain (`:26-33`): the 02 finding L4 is still true. The pod tag cycles `["text-accent","text-ok","text-warn","text-orange","text-bad","text-purple"]` (`MultiLogViewer.tsx:32`), the same hues as cluster identity (the file's own comment says so) and as status. A red tag next to an `ERROR` word reads as an error; 02 §7 and brief Q-L14 say tags need their own `series-1..6`. `tailwind.config.js` has none.

**Proposed:** chips use the level roles the lines already use; add `series-1..6` (non-status hues) for pod tags.

Detail. Chips take the level roles the lines already use (ERROR bad, WARN warn, INFO info, DEBUG dim, no level mute). Add `series-1..6` to `tailwind.config.js` (dark values only, as Q-L14 allows) with six hues that are none of ok, warn, bad, accent, and use them for tags. The compact letters E W I D – (`:346-350`) are kept as the compact form; the expanded form is glyph + word + count (02 §3.4).

### UXP-13 (F2) note: ⌘F, Enter and follow need explicit guards

Evidence. No ⌘F binding exists. `App.tsx:188-196` handles ⌘K and ⌘N. The Logs tab is mounted only while active (`DetailPanel.tsx` content is keyed by tab), which scopes the handler for free. 03 §6.7 and §16 propose ⌘F inside diff dialogs; F3 does not build it, but a dialog can be open over the Logs tab.

**Proposed:** ⌘F is inert while any modal layer is open; jumping to a match turns follow off.

Detail.

- The ⌘F handler returns when `isModalOpen()` is true, so it never steals the key from a diff dialog, and it calls `preventDefault`. Add to the live-verification list: Ctrl+F on WebView2 does not open the native find bar.
- Enter and Shift+Enter move between marks from the Highlight field, and from the log region only when `e.target === e.currentTarget` (the guard `f` and `End` already use at `:272`). Jumping to a mark sets follow to false; otherwise the follow effect (`:213-217`) scrolls it away on the next flush.
- Announce "Match 3 of 17" and the filtered count through the existing sr-only status region (`:404`), not a new live region.

### UXP-14 (F2) note: Download is a menu only when it offers a choice

Evidence. Shipped: one button, downloads everything loaded (`LogViewer.tsx:226-235`, `:393-400`); filename `{pod}-{container}[-previous].log`. 02 §5.1 labels the menu "All loaded lines (5,000)", which would be wrong for the same reason as UXP-9.

**Proposed:** keep the single button until a filter is active, then show the two-item menu with real counts.

Detail (v1.3.0 brief section 1.5 item 1 already replaced the "5,000" framing). When no filter is active, keep the single button (no regression). When any filter is active, it becomes a menu (the shared popover from UXP-6) with "All loaded lines ({loaded})" and "Visible lines ({visible})". "Visible" downloads the `raw` lines (timestamp prefix as received); the filename gets `-filtered`.

### UXP-15 (F2) note: View state is lost on every tab switch

Evidence. Tab content is remounted with `key={pod.name + "-" + tab}` (`DetailPanel.tsx:625`). v1.3.0 already worked around this for the container choice by lifting `logPick` into the panel (`:384`, passed at `:1142`, reset at `:449-451`). Include, Exclude, Highlight, levels and the toggles would otherwise vanish when the user glances at Events and returns.

**Proposed:** lift the View state into `DetailPanel` / `ResourceDetailPanel` like `logPick`; do not persist it.

Detail. Lift the View state the same way: one `logView` object held by `DetailPanel` (reset in the `pod.name` effect) and, for Multi, by `ResourceDetailPanel` (`:3175`, reset on resource change). Do not write it to `localStorage`; only the Source prefs (`log-prefs-*`) persist, and a remembered Exclude would silently hide lines on the next pod.

## F3. Shared diff rows and PREVIEW-GATE

### UXP-16 (F3) blocks F3: the "loading preview" phase must not be `running` or `isPending`

Evidence. `ConfirmModal` ignores Esc and backdrop while `isPending`, and routes Esc to `onEscapeWhileRunning` in `running` (`ConfirmModal.tsx:167-173`). The PREVIEW-GATE opens in "review.loading" and calls `preview_resource_yaml` / `preview_helm_upgrade`. If the host marks that wait as `running` or passes `isPending`, a slow or hung dry-run cannot be backed out of, although nothing has been written.

**Proposed:** preview loading is `phase="review"` with `confirmDisabled`, never `running` or `isPending`.

Detail. Loading is `phase="review"` with `confirmDisabled`, `confirmDisabledReason="Checking with the cluster…"` and an info status line, so Esc and "Back to editor" work. Only the actual Save / Upgrade call uses `isPending` (and `running`). After a failed Save the status slot shows the server error and the diff stays; the editor text is never touched (as v1.3.0 does today).

No other drift in F3: `lg` is `max-w-2xl` (672 px), which is the width 03 draws.

## F5. Drain force-delete

### UXP-21 (F5) blocks F5: the Override band must sit in the pinned footer, below the buttons

Evidence. The deferred pointer line lives in `ResultBody` (`NodeDrainDialog.tsx:425-430`), which is the scrolling body (`ConfirmModal.tsx` children). Replacing it in place puts the Override control **before** the footer buttons in DOM and Tab order. 01 §2.7 requires Tab order Stop, Retry, then Override, below a rule, never reachable from the footer buttons by muscle memory. The attention footer is the custom `footer` at `NodeDrainDialog.tsx:588-598`.

**Proposed:** put the Override band in the attention-phase `footer`, below the buttons; remove the pointer line from `ResultBody`.

Detail. Render the band as part of the attention-phase `footer`, under the button row, separated by a rule; remove the pointer from `ResultBody`. Read-only disables it with the reason.

### UXP-22 (F5) note: the force-delete loop needs states the drain model does not have

Evidence. `DrainRowStatus` is `waiting | evicting | EvictionOutcome` (`utils/drain.ts:14`); `runCounts.done` sums four outcomes; "Retry blocked pods" re-runs only `blocked` rows; the running footer's Stop is checked before each new eviction.

**Proposed:** add a `deleting` row status, return a failed force-delete to `blocked` with its message, and title a clean forced run "Node drained, {n} pods force-deleted".

Detail.

- Add an in-flight row status `deleting`, label "Deleting…". The running banner reads "Force-deleting {n} pods…". Stop applies before each next delete.
- A failed `delete_pod` returns the row to `blocked` with the message "Force delete failed: {server text}". Otherwise it becomes `failed`, which neither Retry nor Override can reach.
- Result title for a clean run with forced pods: "Node drained, {n} pods force-deleted" in the warn tone. The cordon line must not claim the node is empty (it does not today); the default grace period still applies.

## F7. Debug container

### UXP-24 (F7) blocks F7: the debug session state must live above the Shell tab

Evidence. Tab content is keyed `pod.name-tab` (`DetailPanel.tsx:625`), so leaving the Shell tab unmounts the terminal, which stops the session (`ShellTerminal.tsx:89-96`). The brief puts the status strip, the 2 s `get_pod` poll and the started container name in the Shell tab.
