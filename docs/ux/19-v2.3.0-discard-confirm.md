# UX 19: v2.3.0 Observability dialog, discard confirm

Replaces the inline footer prompt ("Discard changes?" / Keep editing / Discard swapped into the footer, `ObservabilityDialog.tsx`) with a stacked `ConfirmModal`. Supersedes `docs/ux/16-v2.3.0-preflight.md` §2.1 "Esc" row (footer wording only; the Esc rules stay) and the "Discard footer" visual check in `docs/ux/17-v2.3.0-acceptance.md` §4 item 2. UX 17 finding S-1 (focus lost when the footer prompt closes) no longer applies, because `ConfirmModal` owns focus return.

## Contract

The dialog renders a `ConfirmModal` as a sibling of its card (not inside it), opened by Cancel or Esc when the draft is dirty. Clean Cancel or Esc still closes at once.

| Prop | Value |
|---|---|
| `open` | the dialog's `discard` state |
| `title` | `Discard changes?` |
| `description` | `Your unsaved edits to the observability settings will be lost.` |
| `confirmLabel` / `cancelLabel` | `Discard` / `Keep editing` |
| `destructive` | default (true): red primary, warning icon, initial focus on the cancel button (Keep editing) |
| `contextLabel` / `contextColor` | the dialog's cluster identity (`identity.label`, `identity.color`), as the hard rule requires |
| `context` | not passed. Discarding local edits is not a cluster write: read-only mode must not block it and the typed-label guard must not ask for the cluster name |
| `onConfirm` | close the dialog without saving |
| `onCancel` | `setDiscard(false)` |
| size | default `sm` |

Remove from the dialog: the footer discard branch, `keepRef`, and the focus-restore effect that existed for it. The dialog's capture-phase Esc handler keeps its `isTopmost()` guard, so with the confirm open (the later layer) it does nothing, and `ConfirmModal` takes Esc, Tab and Ctrl/Cmd+Enter.

## Decisions

**a. Description.** One sentence, no cluster name: the badge above the title already shows it, so repeating it adds a second thing to read. "Unsaved" says why the prompt exists and "will be lost" says what Discard does. No "cannot be undone" (every discard is irreversible, so the phrase adds nothing).

**b. Ctrl/Cmd+Enter and backdrop.** Accept both `ConfirmModal` conventions unchanged. Ctrl/Cmd+Enter fires Discard; it is reachable only after an explicit Cancel or Esc, and the same shortcut confirms every other destructive modal here, so a different rule would be the inconsistency. Backdrop click on the confirm (size `sm`, review phase) means Keep editing; it never reaches the dialog beneath, whose own backdrop stays ignored (UX 16 §2.1). Risk accepted: a user who expects Ctrl+Enter to mean Save loses edits only if the confirm is already open, which they just opened deliberately.

**c. Focus and Esc.**
- Opens on **Keep editing** (`ConfirmModal` destructive default).
- Keep editing, Esc or backdrop closes the confirm and returns focus to the element that had focus when it opened: the field after Esc, or Cancel after a Cancel click. `ConfirmModal` does this itself.
- Discard closes both layers. Focus then follows the dialog's existing chain (opener, else checked range radio, else `[data-panel-heading]`, else `<main>`; `docs/claude/ui.md`, Focus return).
- Esc in the confirm is Keep editing, never Discard. A later Esc in the dialog asks again while the draft is still dirty and closes straight away once it is clean. Esc never discards.

**d. Visual.** Computed from `src/index.css` tokens (`status-bad`, `surface-overlay`), text `text-bad` on `bg-bad/10` over the card:

| Theme | Text | Background | Ratio | WCAG 1.4.3 (12.5 px, 4.5:1) |
|---|---|---|---|---|
| Dark | 248 113 113 | about 53 48 61 | about 4.6:1 | pass, small margin |
| Light | 173 0 23 | about 247 230 232 | about 6.2:1 | pass |

The hover state (`bg-bad/20`) falls to about 4.0:1 in dark. This is the shared `ConfirmModal` primary, used by every destructive dialog, so it is not a v2.3.0 blocker; changing the token or the hover alpha is a codebase task. The border (`ring-bad/30`) and the label carry the button identity in addition to colour, so the red tone is not the only cue (1.4.1).

Double scrim: the confirm's `bg-scrim/60` over the dialog's `bg-scrim/60` gives about 84 % total dimming behind the confirm, and the dialog card itself is dimmed 60 %. Accept. It reads as "dialog on dialog" and keeps the confirm as the only live surface; no `ConfirmModal` change is needed. Revisit only if the first look shows the dialog beneath is unreadable enough to hide that edits exist.

**e. Other points.**
- The dialog is inert while the confirm is open (focus trap, `aria-modal`), so Save state, the Test result and live regions underneath are not reachable; nothing to specify. A late Test or discovery response may still land under the confirm; the dialog's request ids already drop stale ones, and a fresh result is harmless.
- Both modals are `role="dialog"`. A screen reader announces the confirm title and description on open because `ConfirmModal` sets `aria-labelledby` and `aria-describedby` and moves focus into it.
- The confirm is gone when the dialog unmounts (host `key`), so no state leaks to the next open.
- Brief change: none to behaviour. Docs only: `docs/claude/ui.md` lines 149 ("the footer asks") and 154 (last sentence, restore-before-prompt) need rewording in the next docs pass; `06-realtime-fleet.md` rows 696 and 948 are updated here.

## Acceptance checklist

1. Edit a field, press Cancel: a confirm opens over the dialog with the cluster badge, a warning icon, "Discard changes?", the description, **Keep editing** (focused) and a red **Discard**. The dialog footer does not change.
2. Edit a field, press Esc while in a text input: same confirm; Esc again closes the confirm only; focus is back in the input.
3. Cancel button path: Keep editing returns focus to **Cancel**.
4. Discard closes both and focus lands per the chain above (not `<body>`).
5. Clean dialog: Cancel and Esc close at once, no confirm.
6. Ctrl/Cmd+Enter in the open confirm discards; clicking the confirm's scrim keeps editing; clicking the dialog's scrim does nothing.
7. Read-only cluster and a cluster with typed-confirm on: Discard is enabled and asks for no typed label.
8. Tab and Shift+Tab stay inside the confirm; focus never reaches the dialog beneath.
9. Needs the user's eyes: red Discard in dark and light themes keeps the dialog's tone (no heavier than other destructive confirms), double scrim looks acceptable, hover contrast.
