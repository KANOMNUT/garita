## 1. Summary

### R2 Map kind filter

**Minimal version.** Keep the five group chips. Add one **Kinds** button after them that opens a `Popover` with a checklist of the 17 kinds (grouped under the chips' five headings, each with its object count), plus **Show all** and **Hide all**. The hidden state changes from a set of groups to a set of kinds; a chip becomes a shortcut that sets or clears every kind in its group and shows a "some" state when only part of the group is visible. The Graph, the List, the counts and the announcement all read the same set, as they do today.

**Skips (named, with the upgrade path).**

- No "Only this kind" per row. `Hide all`, then tick the wanted kinds, covers it in a few clicks. Upgrade: a per-row `Only` button.
- No bridging across a hidden kind. Hiding ReplicaSets leaves Deployments and Pods unconnected on the canvas. The UI says so (3.7); it does not draw synthetic edges.
- No persistence beyond the page's scope (context and namespace), as the chips behave today.
- Not in the Network policies (approximation) mode: that mode shows pod groups, not kinds.

### R3 YAML find

**Minimal version.** One shared find bar for every YAML view. Case-insensitive literal text, live match count "3 of 12", Enter / Shift+Enter for next / previous, Esc to close. In the read-only view the matches are real `<mark>` highlights. In an edit `<textarea>` the current match is the textarea's own selection (a textarea cannot highlight text), with a "Line 48" readout. Ctrl+F (Cmd+F on macOS) opens it only when focus is inside the YAML view.

**Skips.** Replace, regex, whole word, a match-case toggle, search across tabs, a highlight overview ruler, a saved query, the modal authoring textareas (Create, Merge from file, Helm install) and the diff previews. Upgrade paths: a transparent-textarea overlay for true highlights in edit mode (4.3), an `Aa` toggle.

## 3. R2 Map kind filter

### 3.1 The user's job

"The map has too much on it. Show me only the kinds I care about (Services and Deployments, say), and tell me when something is hidden." The five group chips are too coarse (F1). A graph needs a **multi-select**: a single-select "show only Pods" would draw unconnected boxes.

Heuristics applied: visibility of system status (Nielsen 1) for the hidden-kinds count and the strip sentences; user control and freedom (3) for Show all and the Show all kinds button; error prevention (5) for disabled rows that say why; recognition over recall (6) for counts beside every kind; flexibility and efficiency (7) for chips as the fast path and the popover as the fine one.

### 3.2 Model

- State: a set of hidden **kinds** (`MapKind`, 17 values), replacing the hidden-group set. `KIND_GROUPS` stays as the grouping and the order.
- A group chip is a shortcut over its kinds. Its state is computed over the kinds that have at least one object here (the "present" kinds):
  - all present kinds visible: pressed (as today);
  - none visible: not pressed (as today);
  - some visible: `aria-pressed="mixed"`, pressed styling, and the count reads "11 of 18" (objects of the visible kinds, then the group total). A group with no present kinds keeps the zero-count rule (3.6).
- Click on a chip: pressed (all) hides every kind of the group; mixed or not pressed shows every kind of the group. This is a tri-state checkbox's rule (mixed goes to checked).
- The pipeline order does not change: lineage (focus) first, then hide kinds, then group pods, then count, then the 400 cap (`ui.md`, Frontend pipeline). Only the hide step's input changes.
- The kind filter applies to **Resources** mode only. The Network policies (approximation) mode does not render it.

### 3.3 Layout

### 3.5 Behaviour

1. Toggling a row applies at once (no Apply step, no confirm; it is a view filter). Focus stays on the checkbox. The canvas keeps its pan and zoom: `epoch` already includes the hidden set, and layout depends only on the node and edge sets.
2. **Show all** clears the set. **Hide all** adds all 17 kinds. They are disabled with a reason when they would do nothing: "All kinds are already shown." / "All kinds are already hidden." (`disabledAttrs`, the handler still bails out).
3. After **Hide all** the page shows its existing "All kinds are hidden. Turn a kind back on to see the map." with a new button **Show all kinds** beside the sentence, so the empty state is not a dead end.
4. If a toggle moves the page into the too-many state, or out of it, the filter row remounts. The existing `useRefocus` already puts focus on the Name select (into too-many) or the first graph node (out of it); the popover closes with its row. This is acceptable: the user's goal (get under 400) is met on the toggle that crosses the line.
5. The too-many block's "Or hide kinds:" row gets the same chips and the same **Kinds** button (one `KindFilter` component with the button inside it), so the control is identical in both places.
6. **Group chip click** follows 3.2. The chip keeps the focus-return behaviour it has today (`toggle` calls `requestFocus`).

### 3.6 Zero counts and skipped sources

| Row or chip | Rule |
|---|---|
| Kind with objects | Normal, toggleable. |
| Kind with no objects here, source read fine | Row `aria-disabled`, dimmed, count "0", reason "No objects of this kind in this namespace." (while focused: "... in this chain."). `disabledAttrs(reason)`; click and Space bail out. |
| Kind with no objects because its source was skipped | Same, but the reason is "Couldn't read this kind." and it never says "No objects". The kind-to-source map is in 8 (D5). |
| Group chip, all present kinds | A chip is `aria-disabled` only when the group has no objects **and** none of its kinds is hidden. A group with zero objects whose kinds are flagged hidden (after Hide all) stays clickable, so it cannot trap the user. |
| Hidden kind that later gains objects (refetch) | It stays hidden and the Kinds button's count goes up. |

### 3.7 What hiding means elsewhere on the page

| Surface | Rule |
|---|---|
| Graph and List | Both read the same hidden set (`hideKinds` in `prepareMap` and in the List's `flat`). They never diverge. |
| Scope line | Unchanged. It counts the narrowed set before hiding and grouping (UX 18 N5). |
| Search (TopBar) | Matches stay computed on the shown nodes. The match line gains a hidden-kinds tail so a search cannot lie: `3 matches. 2 more in hidden kinds.`; with none shown and some hidden: `No match in the shown kinds. 2 in hidden kinds.`; with none anywhere: `No match on the map.` (unchanged); when nothing is hidden the old copy is unchanged. The hidden-kind count comes from `matchIds` over the narrowed nodes minus the shown ones. |
| Details strip and accessible name | An edge to a hidden kind is not listed (it cannot be reached), so the strip adds one line: `1 connection goes to a hidden kind.` / `3 connections go to hidden kinds.` When a node has no connections among the shown kinds but has some to hidden ones, the strip says `No connections among the shown kinds. 2 go to hidden kinds.` instead of "No connections found for this object. ...". The node's accessible name ends "No connections among the shown kinds." instead of "No connections." whenever any kind is hidden. The List's row text follows the same sentence. |
| Focus banner | Unchanged. If the focused object's own kind is hidden, the banner still describes the chain (UX 18 N4); the Kinds button shows the hidden count, which is the explanation. |
| Announcement | New polite message after a toggle (debounced 400 ms, so a burst announces once): `2 kinds hidden. 27 objects, 31 connections shown.` / `All kinds shown. 41 objects, 63 connections.` Counts are the prepared (shown) set. It uses the page's existing live region. |
| Legend | Unchanged. |
| Palette, saved searches | Unchanged. The kind filter is not saved. |

No bridging: hiding a kind between two connected kinds leaves the two unconnected, and the strip sentence above is the disclosure. See question Q3.

### 3.8 Persistence

Page state, in `MapPage`, the same lifetime as `hidden` today: reset when the context or the namespace changes, kept across a focus change, the Graph/List switch and the mode toggle, kept while the page is hidden (it mounts hidden). Never written to `localStorage`. Reason: a filter that silently follows the user into another namespace hides objects they did not choose to hide; the Kinds button's hidden count would show it, but a reset is the safer default. See question Q2.

### 3.11 Accessibility

- WCAG 4.1.2: the Kinds button exposes `aria-expanded` and a name that includes the state; the chips expose `aria-pressed` (`mixed` for partial). WCAG 1.4.1: the partial state is carried by the text "11 of 18", not by colour. WCAG 4.1.3: the announcement in 3.7 reports the result of a toggle without moving focus. WCAG 2.1.1 / 2.1.2: every control is operable by keyboard and nothing traps (the popover is not a focus trap). WCAG 2.4.3: focus order follows the visual order.
- Focus indicators on the new controls: `focus-visible:ring-2 focus-visible:ring-accent/70 outline-hidden` (the `MapPage` `btn` pattern). Computed: accent at 70 % over the panel is about 3.8:1 in dark and 3.7:1 in light, above the 3:1 of WCAG 1.4.11. The old `focus:ring-accent/40` pattern is lower and is not used for new controls. Polish: give the existing chips the same ring (they have none of their own).
- Text uses `ink` and `mute`, never `dim` (fails AA as text).

## 4. R3 YAML find

### 4.1 The user's job

"I opened the YAML of a resource with 600 lines. Where is `replicas`, or the image tag, or `nodeSelector`?" Ctrl/Cmd+F is the reflex. In a Tauri webview it does nothing useful on macOS and is unreliable elsewhere, so the app supplies it.

Heuristics applied: flexibility and efficiency (Nielsen 7) for the platform shortcut and Enter / Shift+Enter; visibility of system status (1) for the live "3 of 12" count; help users recover (9) for the "Search full object" and redaction hints when nothing is found; error prevention (5) for disabled previous / next with a reason; consistency (4) for one find in all three YAML views.

### 4.2 Surfaces

| ID | Surface | Read view | Edit view |
|---|---|---|---|
| Y1 | Generic panel, YAML tab (`ResourceDetailPanel.tsx:3609`): every kind with a YAML tab, CRD instances and revealed Secrets included | `<pre>`, plain or Neat | `<textarea>` |
| Y2 | Pod panel, YAML tab (`DetailPanel.tsx:1398`) | `<pre>`, plain or Neat | `<textarea>` |
| Y3 | Helm release, Values tab (`ResourceDetailPanel.tsx:3473`) | `<pre>`, redacted or revealed | `<textarea>` |

Out: a Secret's YAML tab before Reveal (it is a placeholder card with one button; there is no text, so no find control is shown and Ctrl+F is inert there); the loading skeleton; the Create, Merge-from-file and Helm-install textareas (modal authoring surfaces, small documents, focus-trapped); the diff and preview rows (`DiffRows`); the Compare dialog; the log viewers (they keep their own Ctrl+F); the shell terminal. One component serves Y1 to Y3 (D1, section 8).

### 4.3 Decision: how matches are shown

A `<textarea>` cannot style part of its text, and the CSS Custom Highlight API does not reach inside it (and needs Safari 17.2 / Chromium 105, above this app's floor). Three options:

| Option | What the user sees | Cost and risk | Verdict |
|---|---|---|---|
| A. Selection-based find | The current match is the textarea's own selection; other matches are not marked. | Small. Needs a scroll-into-view for the textarea (WKWebView does not scroll a textarea on `setSelectionRange`). When the find input has focus the selection paints in the inactive colour (grey), which is weak. | **Edit view.** Mitigated by the "Line 48" readout. |
| B. Overlay | A `<pre>` mirror behind a transparent textarea, marks drawn in the mirror. All matches visible. | Medium to high. The mirror must match font, padding, wrapping and scroll position exactly; it drifts on WebKitGTK and with scrollbars; two copies of the text for assistive tech. | Not now. Named upgrade if A tests badly. |
| C. Read view for edit | Highlight in a read-only copy, edit elsewhere. | Changes the editing model. | Rejected. |

The read-only `<pre>` is ordinary DOM, so it gets real highlights (a text node split into text and `<mark>` children) with no such limits. **Decision: `<mark>` in the `<pre>`, option A in the `<textarea>`.**

### 4.4 Scope of the shortcut

- Platform: **Cmd+F on macOS, Ctrl+F elsewhere**; the other combination is left alone. On macOS `Ctrl+F` is "cursor forward" in text fields and must not be hijacked. The platform test is the user-agent test `updateMode` already uses (`/macintosh|mac os x/i`); put it in one shared helper (D6).
- The handler is a React `onKeyDown` on the YAML view's root element, not a window listener (unlike the log viewers). The YAML view's root contains: the toolbar, the Neat note, the find bar, and the `<pre>` or `<textarea>`.
- It acts only when all of these hold: the platform combination matches with no Shift or Alt; `isModalOpen()` is false; `root.contains(event.target)` (DOM containment, because `YamlSaveGate` bubbles through React from a portal, F12); the event is not `isComposing`. Then it calls `preventDefault()` and opens the bar. In every other case it does nothing, so the webview's and every other panel's behaviour is unchanged, and the Logs tab keeps its own handler.
- `e.key.toLowerCase() === "f"`, as the log viewer does. A layout that does not produce a Latin "f" will not trigger it (same as the log viewer).
- Consequence: right after clicking the **YAML** tab, focus is on the tab button, which is outside the view, so Ctrl+F does nothing until focus is in the view. Two things close that gap without widening the scope: the `<pre>` is now focusable, so one click into the text puts "the cursor" in the YAML (F8); and the toolbar has a visible **find** button whose tooltip names the shortcut. See question Q4.

### 4.6 Behaviour

1. **Open.** Ctrl/Cmd+F in the view, or the find button. The bar appears, the input gets focus and its text is selected. If the user had selected text, it prefills the input (a single line, 1 to 120 characters, taken from the displayed text only: the `<pre>` selection inside the view, or the textarea's selection); otherwise the previous query for this view, if any, is kept. The element that had focus is remembered as the opener.
2. **Query.** Case-insensitive, literal (no regex, no wildcard, no trimming; a query of only spaces counts as empty). Matches update as the user types (the input value is deferred so a large document stays responsive). The first current match is the first at or after the caret in the textarea, and the first in the document in the `<pre>`.
3. **Navigate.** `Enter` or the next button: next match, wrapping to the first after the last. `Shift+Enter` or previous: the reverse. `Cmd+G` (macOS) / `Ctrl+G` (elsewhere, the same platform rule as 4.4) and the Shift forms do the same from anywhere in the view while the bar is open (so a user who clicked back into the text keeps stepping). Enter inside an IME composition (`isComposing`) does nothing.
4. **Reveal the current match.**
   - `<pre>`: the current mark scrolls into view with `block: "nearest"`, `inline: "nearest"`, `behavior: "auto"` (no smooth scrolling, so `prefers-reduced-motion` is respected), with `scroll-mt-14` so the sticky bar never covers it.
   - `<textarea>`: set the selection to the match and set the textarea's `scrollTop` so the match's line sits at least two lines inside the visible area (measure the line with a hidden mirror element that copies the textarea's font, padding and width, because the lines wrap; do not assume a fixed line height). Focus stays in the find input, so Enter keeps stepping. The outer tab scroller is also adjusted so the textarea is on screen.
5. **Close.** `Esc` or the close button or the find button. Marks disappear. Focus returns to the opener if it still exists, else to the `<pre>` / `<textarea>`, else to the find button. In the textarea the current match stays selected (the browser and editor convention), so the user can type the new value at once; the edit still goes through the Review & save gate and native undo. The query is kept for this view, so reopening restores it.
6. **Ctrl/Cmd+F with the bar open.** Focuses the input and selects its text; it does not toggle.
7. **Editing while the bar is open.** Matches recompute from the live buffer; the current index is clamped; the caret and scroll are not touched (the find never moves the selection except on explicit navigation or typing in the find input).
8. **Switching read to edit (or back) with the bar open.** The bar and query stay; the surface changes from marks to selection. Neat on to off, the same.
9. **Lifetime.** The bar state lives with the view. It resets (closed, empty query) when the selected object changes, when the YAML or Values tab is left (the tab body remounts), when a Secret or Helm reveal ends (Hide), and when the panel closes. See 4.7.

### 4.7 Text, Neat and Secrets

**The one rule: the find reads exactly the string that is rendered, nothing else.** It uses the same variable passed to the `<pre>` or `<textarea>` (`shownYaml` for the read view, `editContent` for the edit view, the displayed Helm text for Values). It never reads a query cache, `get_resource_json`, the other Neat variant, or any unmasked source.

| Case | Searched text | Notes |
|---|---|---|
| Read, Neat off | `yamlContent` | Includes managed fields and status. |
| Read, Neat on and loaded | the neat YAML | If there are no matches and the neat view hides fields, the hint line says `Not found in the neat view. Managed fields, status and other server-set fields are hidden.` with a button `Search full object` that turns Neat off (the find state survives the toggle). |
| Edit | `editContent` | The full object, including `managedFields` and `status` (the editor already shows them). |
| Secret YAML, not revealed | nothing | Placeholder card. No find control, Ctrl+F inert. |
| Secret YAML, revealed | the revealed YAML | The values are on screen by the user's per-object Reveal; searching them adds no exposure. |
| Helm Values, redacted | the redacted text | Credential-looking values are `<redacted>` in the string, so they cannot be matched, and the count never reflects them: there is no oracle for a guessed password. With no matches the hint line says `Not found. Values under credential-looking keys are redacted in this view.` |
| Helm Values, revealed or editing | the revealed text | As Secret revealed. |

Lifetime rules, all four testable:

- **S1.** Match state is derived from the rendered string, so when that string becomes empty or masked (Hide, close, selection change) it is zero matches.
- **S2.** The bar's state is reset by a key made of the object identity plus the reveal flag (`resetKey`), so a query typed or prefilled from a revealed value never survives Hide, a selection change or a context change. The view is mounted under `key={idKey}` for the same reason.
- **S3.** The query is never persisted: no `localStorage`, no saved searches, not sent through `invoke`, not written to the app log or journal.
- **S4.** Announcements speak counts and positions only, never the query text.

### 4.10 Accessibility

- **The `<pre>` becomes a named, focusable region** (F8): `tabIndex={0}`, `role="region"`, `aria-label="<Kind> <name> YAML"` (Values: "<release> values"), focus ring `focus-visible:ring-2 focus-visible:ring-accent/70 outline-hidden`. This satisfies WCAG 2.1.1 for a scrollable region and 4.1.2 for its name, and it is what makes "focus inside the YAML" real for the mouse and the keyboard. A `<pre>` has no role, so a name alone would be ignored.
- **Names.** Bar `role="search"` named "Find in YAML". Input `aria-label` "Find in YAML". Buttons named as in 4.5.
- **Live region.** One `role="status"` `aria-live="polite"` `sr-only` element, separate from the visible count. It speaks: after the user pauses typing (500 ms debounce, not on each keystroke) `12 matches` / `1 match` / `No matches`; on each step `3 of 12` (textarea: `3 of 12, line 48`; after a wrap: `1 of 12, wrapped`). It never repeats the query (S4).
- **Marks.** `<mark>` is the correct element for a relevance highlight; some screen readers announce it. The bar and the live region are the primary route for assistive technology, so the marks add no required step. The text of a mark is unchanged, so selection and copy are unaffected.
- **Colour and contrast.** The current match is not colour alone: it is also underlined (`underline decoration-2 underline-offset-2`, as `LogLine` does) and it is the match the count and the "Line" readout refer to (WCAG 1.4.1). Contrast of `ink` text on the mark backgrounds, computed from `src/index.css` (marks sit on `surface-sunken`):

  | Mark | Dark | Light |
  |---|---|---|
  | All matches (`log-match`) | about 10.4:1 | about 4.8:1 |
  | Current (`log-highlight`) | about 6.5:1 | about 4.9:1 |

  All pass 4.5:1 (WCAG 1.4.3). The marks never follow the accent (the `log-*` roles), so a teal or rose accent leaves them unchanged.
- **Reduced motion.** No animation on the bar; no smooth scroll.
- **Zoom and reflow.** The bar is one flex row that fits 296 px; nothing needs two-axis scrolling (WCAG 1.4.10, 1.4.4).
- **Input boundary.** The input uses the app's `ring-edge` boundary like the TopBar search. It is identified by its placeholder, label and position, which WCAG 1.4.11 accepts; this is not new.

## 9. Questions for the user (with recommended answers)

**Answers (2026-10-27).** The user answered Q1 (keep both), Q3 (no bridging in v2.3.1) and Q6 (yes, Helm Values included), each as recommended. Q2, Q4, Q5 and Q7 were not put to the user; the recommended answers stand unless the user overrides them. Separately, the user put the ArgoCD list's bulk "Select all" ignoring the TopBar search into v2.3.1 as a fix; it is planned in `docs/impl/v2.3.1-tasks.md`, not here.

**Q1. Map: keep the five group chips next to the new Kinds dropdown, or replace them with it?**
Recommended: **keep both.** The chips are the fast path for the common cases (hide Config, hide Scaling) and keep their counts visible; the dropdown is for the fine cases. Replacing the chips costs a click for every group toggle and removes the at-a-glance counts. The two share one state, so they cannot disagree.

**Q2. Map: should the kind filter be remembered across namespaces or restarts?**
Recommended: **no.** Keep today's rule: it resets when the context or the namespace changes. A filter that follows you into another namespace silently hides objects you did not choose to hide. If you want a default (say, always hide ReplicaSets), it is a small follow-up: a per-viewer "Remember my kinds" setting.

**Q3. Map: when you hide a kind in the middle of a chain (for example ReplicaSets), should the map draw a direct Deployment-to-Pod edge instead of leaving them unconnected?**
Recommended: **no, not in v2.3.1.** Bridging means synthetic edges, new labels ("owns, via ReplicaSet"), de-duplication and a change to the lineage pipeline. The details strip and the node names already say "go to hidden kinds", so nothing is misleading. If hiding ReplicaSets is the main use you see, say so and it becomes its own task.

**Q4. YAML: after you click the YAML tab, Ctrl/Cmd+F does nothing until you click into the text, because focus is still on the tab button. Is that acceptable, or should Ctrl/Cmd+F also work whenever the YAML tab is selected?**
Recommended: **keep the scope as you asked (focus inside the YAML).** The text is now focusable, so one click puts the cursor in it, and the toolbar has a visible **find** button that shows the shortcut. Widening it to "anywhere in the open panel" makes the shortcut depend on which tab is selected and brings back the risk of taking Ctrl/Cmd+F from other controls.

**Q5. YAML: in the edit view the current match is shown as the textarea's own selection (grey while the find box has focus), with a "Line 48" readout, not as coloured marks. Is that enough?**
Recommended: **yes for v2.3.1.** True highlights in a textarea need an overlay that has to match the font, wrapping and scrolling exactly and tends to drift on some webviews. Ship the selection, look at it in the three webviews, and build the overlay only if it reads badly.

**Q6. YAML: should the Helm release Values tab get the find too?**
Recommended: **yes.** It is YAML text with the same read and edit views; with the shared component it costs almost nothing, and its redaction behaviour is specified (4.7).

**Q7. YAML: the Create, Merge-from-file and Helm-install dialogs have YAML textareas. Include them?**
Recommended: **no.** They are small authoring surfaces inside focus-trapped dialogs, and a find bar there competes with the dialog's own keys. The shared component can be added to them later.
