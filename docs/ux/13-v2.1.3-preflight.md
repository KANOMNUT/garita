Status: preflight for the DRAFT brief `docs/impl/v2.1.3-tasks.md`. Not a new spec. It supersedes `docs/ux/05-theme-settings-platform.md` §10 wherever they differ; §10 predates the rebrand.

- Tags: RUST-AFFECTING (changes a Rust contract or output), FRONTEND, SITE.

## P0

### 1. RUST-AFFECTING: `LaunchArgs.ignored` must carry every token the parser did not consume

Problem: the contract says `kind` is `None` "if absent or unrecognised" and `ignored` holds "tokens that were not understood". An unrecognised kind (`garita pdos`) is then indistinguishable from no kind, so the UI cannot say anything (Nielsen: visibility of system status, error recovery). A lone `-n`, `--context` with no value, and a second positional have the same hole.

Fix (parser behaviour, all covered by `parse_launch_args` tests):

- An unrecognised positional goes into `ignored` verbatim, `kind` stays `None`.
- A second and later positional go into `ignored`.
- A value flag with no value (`-n` last, `--context` last, or `-n --context x`) puts the flag token into `ignored` and does not swallow the next flag.
- `--context=x` and `-n=x`/`--namespace=x` forms are accepted; `-nfoo` is not (goes to `ignored`).
- macOS launch-services noise (`-psn_*`) is dropped silently, not reported.
- Values of consumed flags never appear in `ignored`.
- Frontend then needs exactly one "ignored" message for flags, kinds and positionals (finding 4); no separate "unknown kind" path.

### 2. RUST-AFFECTING: who prints the unknown-argument line, and precedence

Problem: UX-05 specifies a stderr line for unknown options, but T52-7 re-spawns the process with stdio set to null and T52-6 gives the Windows GUI build no console. As written the line is printed by nobody on two paths.

Fix:

- The **launching** process prints before it detaches (Unix) or starts the builder. The detached child prints nothing. Exit code stays 0 (not an error).
- Lines, one per ignored token, to stderr, only when stdout/stderr is a terminal:
  - unknown flag: `garita: ignoring unknown option '--foo' (see garita --help)`
  - unrecognised kind or extra positional: `garita: ignoring unknown resource type 'pdos' (see garita --help)`
  - flag without value: `garita: option '-n' needs a value (ignored)`
- Windows: these lines are **not printed** (T52-6 attaches a console only for `--help`/`--version`). The strip in finding 4 is the only feedback there. State this in `docs/claude/launcher.md`; do not widen the console attach.
- Precedence: `--help` wins over `--version` wins over everything else, regardless of order or unknown neighbours. `--help` with unknown options still prints help and exits 0.
- Values echoed to stderr or `ignored` are untrusted text: cap each at 64 characters (`...` suffix) so a pasted blob cannot flood the strip.

### 3. FRONTEND: a forwarded request never changes state under an open dialog

Problem (Nielsen: user control, error prevention): T52-9 validates the context but is silent on timing. A context switch under a half-read destructive dialog is the exact hazard UX-05 §10.2 named.

Fix, one rule for every forwarded request (second instance only; see finding 9 for the first instance):

- "Dialog open" is `isModalOpen() || overlayOpen` (`src/utils/modalLayer.ts`; `overlayOpen` in `App.tsx` covers switcher, palette, creator, merge-from-file, Helm install). This includes a `ConfirmModal` in its `running` state, so a write in flight inside a dialog is covered.
- If open: apply **nothing** (context, namespace and kind are deferred together, because namespace and kind belong to the requested context). Show the deferral strip (finding 4). The OS-level window raise still happens (Rust side, T52-8); only app state is held.
- The strip button **Go now** applies the held request. It is only enabled when no dialog is open: `aria-disabled` with `aria-describedby` pointing at the strip text, reason "Close the open dialog first." (disabled controls show their reason, never hidden). Nothing applies automatically when the dialog closes; the user presses the button.
- The held request is dropped if the user switches context themselves, or a newer forwarded request arrives (latest wins, one strip).
- No dialog open but a write in flight outside a dialog (a mutation still pending after its modal closed): apply immediately. Writes carry their own explicit context; the in-flight call is unaffected. No extra copy.
- Read-only mode does not change anything here. Launch args only select state and never write. The cluster switched to shows its normal Read-only chip. No read-only wording in the strip.

### 4. FRONTEND: one coherent copy set (replaces both T52-9's toast and UX-05's strip texts)

One strip component, one live region, never a toast. Neutral variant (as `UpgradeSeedBanner`), `role="status"`, a `✕ Dismiss` button (`aria-label="Dismiss"`), no auto-dismiss, no focus steal (the user is coming from a terminal; focus stays where the window put it). New cost: one small `LaunchNoticeStrip` function in `App.tsx` beside the existing banners; no new infrastructure. At most one strip: a new forwarded request replaces the previous strip.

Lines (each is one `<p>`; several can stack in the same strip):

| Case | Copy |
|---|---|

| Context unknown | `Context 'foo' not found; staying on 'bar'.` |
| Namespace unknown (checked once the namespace list of the target context has loaded) | `Namespace 'x' not found in 'foo'; staying on 'kube-system'.` Use `All namespaces` as the current-value label when none is selected. |

- The kind is applied as the view; the strip never repeats a successful namespace or kind (the view and the namespace chip are the feedback). Only the context switch gets a success line because changing cluster is high-consequence.
- Cluster-scoped kind plus a namespace (`garita -n x nodes`): the kind view hides the namespace picker (`viewHidesNamespacePicker`), so the namespace is dropped silently, no strip line.
- Unmappable kind on the frontend (Rust recognised it, `ResourceType` lacks it): treated as an ignored token, same line.
- Esc: the strip does not register a modal layer and does not handle Esc. Esc keeps its existing meaning.

## P1

### 6. RUST-AFFECTING: `CliStatus` semantics the UI needs

The struct is sufficient only if Rust fills it with these meanings. Without them the UI cannot tell "not installed" from "stale link".

- `on_path`: `garita` resolves to **this app's** binary. `resolved_path`: what it resolves to, when it resolves at all (so `on_path=false` with `Some(p)` means a stale or foreign link; `None` means absent). The UI prints `resolved_path`, never a hard-coded `/usr/local/bin/garita` (a Homebrew cask `binary` stanza puts the link elsewhere and must read as installed).
- macOS `manual_command`: always populated. Quote the app path (spaces). If `/usr/local/bin` does not exist (common on Apple Silicon without Homebrew in `/usr/local`), the line is `sudo mkdir -p /usr/local/bin && sudo ln -s "<exe>" /usr/local/bin/garita`; otherwise `sudo ln -s "<exe>" /usr/local/bin/garita`. Use `ln -sf` only when the existing entry is a link (stale), never over a regular file.
- macOS install denied: `Ok` with `on_path=false` and `manual_command` set (as the brief). Foreign file: the `Err` text in the brief, with the app name: `Failed to install command: /usr/local/bin/garita already exists and is not Garita's link`.
- Windows: derive `on_path` from the **user PATH in the registry** (`HKCU\Environment`), not the process environment. The process PATH is stale until the app is relaunched after the installer ran, so reading it would report a fresh install as "not on PATH".
- AppImage: `manual_command` uses the AppImage file path (the `APPIMAGE` environment variable), not `current_exe()`, which points into the temporary mount and dies on exit. Line: `ln -s "<AppImage path>" ~/.local/bin/garita`.
- Linux package: `on_path` is true when `/usr/bin/garita` exists and resolves to `/usr/bin/<binary>`; `resolved_path` is that link.
- `install_cli_command` is a local file operation, not a cluster write: it stays out of `invokeWrite()` and works in read-only mode. `writeBackstop.test.ts` must not list it. The hook lives in `useResources.ts` (components never call `invoke`).

### 9. FRONTEND: forwarded-args behaviour matrix

| Situation | Behaviour |
|---|---|
| First instance (`get_launch_args`) | Apply context, then namespace, then kind (order from F1). No success strip. Problem lines (unknown context, unknown namespace, ignored tokens) show the strip. No dialog can be open at startup, so no deferral. |
| Second instance, no dialog | Apply in the same order, then the lines of finding 4. |
| Second instance, dialog open | Defer all; finding 3. |
| Context valid but equal to the current one | No switch line; apply namespace and kind. |
| Settings view or a non-resource app view is showing | Navigating to the kind goes through the `setActiveResource` wrapper, which leaves Settings. If the request had no kind, stay where you are. |
| Selected object or detail panel open | A context switch clears the selection exactly as a manual switch does. A namespace or kind change without a context change follows the same path as picking them in the UI. No special handling. |
| Context disabled in the registry | Same as unknown (`list_contexts()` only returns enabled ones). |
| Second instance but `launch-args` arrives before the webview has registered the listener | Rust holds the latest payload for `get_launch_args` (already the first-instance path); no extra UI. |

### 12. RUST-AFFECTING: `--help` and `--version` text

Constants: `PRODUCT_NAME` and `CLI_COMMAND_NAME` ("garita"), version from `CARGO_PKG_VERSION`. Print to stdout, exit 0. The text lives in Rust; the UI does not duplicate it (finding 13).

```
Garita 2.1.3: Kubernetes desktop client

Usage:
  garita [options] [kind]

Options:
  --context <name>         Open with this kubeconfig context selected
  -n, --namespace <name>   Open with this namespace selected
  -h, --help               Show this help and exit
  -V, --version            Show the version and exit

Kind:
  A resource type to open, such as pods, deployments or services.
  kubectl short names work: po, deploy, svc, ing, cm, secret, no, ns.

Examples:
  garita --context prod -n kube-system pods
  garita deploy

Running garita while Garita is open brings that window to the front and applies these options.
```

- `--version` prints one line `Garita 2.1.3`.
- Short names in the help line must be exactly the keys of the one mapping table (T52-1); add a test that every name printed in the help resolves, so the help cannot drift from the table.
- The help names only flags that exist (UX-05 rule kept).
